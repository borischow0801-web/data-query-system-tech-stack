### 1. 四条办件无法归属部门

以下行号均为对应响应 `list` 的从 1 开始计数的位置，可以通过历史结构化回放核对：

| 历史 ID | 请求页号 | 响应行号 | 已确认缺失 |
| --- | --- | --- | --- |
| 83 | 1 | 282 | `acceptdeptcode`、`acceptdeptname`、`taskcode` |
| 84 | 2 | 777 | 同上 |
| 84 | 2 | 863 | 同上 |

这 4 条记录有 `projid`、`itemno` 和事项名称，但无法从返回的部门字段确定所属部门。不能擅自依据事项名称猜测部门，也不能直接删除后称作全部办件。

建议：请接口方补充部门名称及代码，或提供经确认的办件/事项目录映射。若允许带缺失值交付，可明确授权将这 4 条单列为“部门待确认”，保留在总量核验中，不分配给任何已知部门。

### 2. 需要区分事项唯一键与办件唯一键

项目字段说明分别定义：`itemno` 为“审批事项编号”、`taskcode` 为“实施编码”、`catalogcode` 为“基本编码”。用户所说的事项 code 目前没有唯一映射到其中一个字段。

6 组同一 `projid` 对应不同 `itemno` 和 `taskcode`，但部门代码相同。这可能是一办件关联多个事项，也可能是上游数据问题；本次不能据此判断哪一行应该保留。

| 历史 ID | 请求页号 | 同一 `projid` 所在行 |
| --- | --- | --- |
| 172 | 90 | 911、912 |
| 172 | 90 | 948、949 |
| 175 | 93 | 396、397 |
| 175 | 93 | 398、399 |
| 176 | 95 | 234、235 |
| 177 | 94 | 538、539 |

这些组合在同一响应页内同时存在，因此不能简单归因于并发分页重复。

建议由业务方确认：

- 事项分组使用 `itemno` 还是 `taskcode`。字段名不同，汇总粒度也不同，不应仅凭名称相似自动合并。
- 若每行即一条需要计数的事项办件，可按部门和选定事项 code 计行数。
- 若需要去重，明确唯一键是全局 `projid`，还是“部门代码＋事项 code＋projid”等组合。全局 `projid` 去重会舍弃部分事项关联，不能默认采用。
- 同一组合多次出现时应按记录数、唯一办件数还是最新版本计数。需要最新版本时还需确认有效的版本/排序字段。

### 3. 年度口径及零办件部门

已确认本次返回记录的 `applydate` 全部在 2025 年，但参数模板没有明示 `startTime/endTime` 究竟筛选申请、受理、办结或其他业务时间。应请接口方确认；本次结果不能称作“2025 年办结量”。

当前只取得有返回记录的部门，没有完整的市级部门及事项目录，无法确认哪些部门零办件。若“所有部门”包含零办件部门，应提供完整目录，按确认的统计口径补零。
