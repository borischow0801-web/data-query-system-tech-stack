# 数据查询系统技术栈文档

## 1. 文档目的

本文档用于指导“数据查询系统”的设计与开发，供 Cursor 作为实施依据使用。  
系统核心目标如下：

- 对接多个外部业务接口
- 统一处理 SM2/SM4 加解密调用链
- 提供配置化查询能力
- 支持查询结果展示、分析、导出
- 对内提供前端页面使用能力
- 对外提供标准 API，供其他业务系统调用
- 满足后期多接口扩展、日志审计、权限控制、运维监控等需求

---

## 2. 系统定位

本系统不是简单的接口调试工具，而是一个**配置化、平台化、可扩展的数据查询中台**。  
它承担以下职责：

1. **外部接口适配层**  
   统一封装外部接口的鉴权、加密、请求组装、响应解密。

2. **查询执行层**  
   根据接口模板和用户输入参数生成请求，执行查询，并返回标准化结果。

3. **结果处理层**  
   对查询结果进行结构化处理、表格化展示、图表分析、导出下载。

4. **开放服务层**  
   提供标准 REST API / 内部服务接口，供其他业务系统复用。

---

## 3. 总体技术选型原则

### 3.1 技术选型原则

- 后端优先采用 Python 技术栈，便于快速开发与接口适配
- 前后端分离，便于后续扩展与多端接入
- 加解密、Token、接口配置全部放在服务端处理
- 接口规则配置化，避免写死
- 查询结果标准化，支持页面展示与外部系统调用
- 支持后续从“单次查询”扩展到“定时拉取、数据沉淀、分析报表”
- 满足政务类项目对日志、审计、安全、权限、可追溯的要求

### 3.2 架构设计原则

- **高内聚、低耦合**
- **配置优先**
- **可观测**
- **可扩展**
- **可审计**
- **兼容多接口、多环境、多调用方**

## 4. 总体架构建议

建议采用如下分层架构：

```text
前端展示层
  ├─ 查询页面
  ├─ 接口配置管理页面
  ├─ 查询结果展示页面
  ├─ 图表分析页面
  └─ 日志审计页面

应用服务层
  ├─ 用户与权限模块
  ├─ 接口配置模块
  ├─ 参数模板模块
  ├─ 查询执行模块
  ├─ 结果分析模块
  ├─ 导出模块
  ├─ 开放 API 模块
  └─ 日志审计模块

接口适配层
  ├─ SM2/SM4 加解密适配
  ├─ Token/Header 组装
  ├─ HTTP 请求封装
  ├─ 多接口协议适配
  └─ 响应解密与标准化转换

基础设施层
  ├─ MySQL / 瀚高（MySQL兼容）
  ├─ Redis
  ├─ 文件存储
  ├─ 日志系统
  ├─ 任务调度
  └─ 监控告警
```

## 5. 推荐技术栈

## 5.1 前端技术栈

推荐方案：

- **框架**：Vue 3
- **构建工具**：Vite
- **语言**：TypeScript
- **UI 组件库**：Element Plus
- **状态管理**：Pinia
- **路由**：Vue Router
- **HTTP 请求**：Axios
- **图表库**：ECharts
- **表格能力**：
  - 基础表格：Element Plus Table
  - 高级表格（可选）：vxe-table
- **导出能力**：
  - 前端轻量导出：xlsx
  - 大文件导出建议走后端生成

### 前端选型理由

选择 Vue 3 + Element Plus 的原因：

- 政务类后台管理系统开发效率高
- 表单、表格、弹窗、树结构等场景成熟
- 方便做“动态参数表单”“配置管理页面”“日志页面”
- 便于快速搭建运营类、管理类页面

### 前端主要页面建议

1. 登录页
2. 首页 / 工作台
3. 接口配置管理页
4. 参数模板管理页
5. 查询执行页
6. 查询结果详情页
7. 图表分析页
8. 历史查询记录页
9. 调用日志页
10. 外部调用方管理页
11. 系统配置页

## 5.2 后端技术栈

推荐方案：

- **语言**：Python 3.11+
- **Web 框架**：FastAPI
- **ASGI 服务**：Uvicorn / Gunicorn + UvicornWorker
- **ORM**：SQLAlchemy 2.x
- **数据校验**：Pydantic v2
- **数据库迁移**：Alembic
- **HTTP 客户端**：httpx
- **任务调度**：
  - 简单定时任务：APScheduler
  - 若后期任务较多：Celery + Redis
- **缓存**：Redis
- **日志**：Loguru / Python logging
- **导出能力**：
  - Excel：openpyxl / pandas
  - CSV：内置 csv / pandas
  - PDF（若后续需要）：reportlab 或 wkhtmltopdf 路线
- **图表分析计算**：
  - pandas
  - numpy
- **接口文档**：FastAPI 自带 OpenAPI / Swagger

### 后端选型理由

选择 FastAPI 的原因：

- 开发效率高，适合快速搭建中台型系统
- 原生支持 OpenAPI，便于后续给其他业务系统开放接口
- 类型定义清晰，利于 Cursor 按规范生成代码
- 对外 HTTP 调用、参数校验、异步接口、内部 API 都比较友好
- 适合配置化接口平台的快速演进

## 5.3 数据库技术栈

推荐方案：

- **开发环境**：MySQL 8
- **生产环境**：瀚高数据库（按 MySQL 兼容 SQL 规范设计）
- **字符集**：utf8mb4
- **存储引擎**：InnoDB（开发环境）
- **连接驱动**：
  - MySQL：pymysql / asyncmy
  - 瀚高：根据生产环境兼容驱动适配

### 数据库设计原则

- 表设计遵循 MySQL 8 兼容写法
- 避免使用过于依赖单一数据库特性的 SQL
- 尽量不使用复杂存储过程作为核心业务逻辑
- 核心业务逻辑放到应用层
- JSON 字段可用，但关键查询条件不依赖 JSON 深层检索
- 所有配置类、日志类、模板类数据都留扩展字段

---

## 5.4 缓存与任务技术栈

### Redis

用途建议：

- token 缓存
- 热门接口配置缓存
- 参数模板缓存
- 查询结果短时缓存
- 防重复提交控制
- 异步导出任务状态缓存

### 定时任务

建议分阶段实施：

#### 第一阶段
- 使用 APScheduler 实现基础定时任务
- 用于定时同步接口配置、定时报表拉取、定时清理历史缓存

#### 第二阶段
- 若出现大量异步任务、导出任务、批量调度任务
- 升级为 Celery + Redis

---

## 5.5 加解密技术栈

这是本系统最关键的基础能力之一。

推荐封装为独立模块：

- **国密算法支持库**：
  - 优先评估对方提供的官方工具类 / demo
  - Python 国密库候选：
    - gmssl
    - gmssl-python
    - 其他经验证可用的国密实现
- **封装策略**：
  - 独立封装 `crypto_service`
  - 独立封装 `sm2_service`
  - 独立封装 `sm4_service`
  - 独立封装 `hybrid_encrypt_service`

### 加密模块必须支持的能力

1. 生成随机 SM4 密钥
2. 使用指定 SM4 模式加密 data
3. 使用指定 SM4 模式解密响应
4. 使用 SM2 公钥加密 SM4 密钥
5. 兼容不同 SM2 密文格式（如 C1C2C3 / C1C3C2）
6. 兼容 Base64 / Hex 编码
7. 配置化指定 header 字段名
8. 配置化指定请求体密文字段名
9. 配置化指定响应密文字段名

### 重要约束

- 所有加解密逻辑必须在后端执行
- 前端不得保存 token、公钥私密配置、加密中间结果
- 加解密规则必须可配置，不允许硬编码为单一接口规则

## 5.6 对外开放 API 技术栈

系统后期要支持“别的业务系统调用本查询系统”，因此必须从一开始就考虑 API 化设计。

推荐：

- **协议**：RESTful API
- **格式**：JSON
- **认证方式**：
  - 内部系统：AppKey + AppSecret / AccessToken
  - 同域系统也可接入 JWT
- **限流**：
  - 网关限流或应用内限流
- **接口文档**：
  - OpenAPI / Swagger
  - 对外提供字段说明、示例报文、错误码说明

### 对外 API 的建议能力

1. 查询接口列表
2. 获取指定接口参数模板
3. 发起查询请求
4. 获取查询结果
5. 获取导出文件下载地址
6. 获取历史任务状态
7. 获取标准错误码与异常信息

该模块是平台化能力核心。

建议配置内容包括：

### 基础配置
- 接口名称
- 接口编码
- 接口分类
- 请求方式
- 请求 URL
- 超时时间

### 安全配置

- token header 名称
- SM2 公钥
- SM2 密文格式
- SM4 模式
- SM4 填充方式
- 密文编码方式

### 报文配置
- 请求 header 模板

- data 字段名

- 响应 data 字段名

### 扩展配置
- 重试次数
- 重试间隔
- 限流阈值
- 结果缓存时间

- 接口配置单独建表

- 支持启停状态
- 支持导入导出配置

- 参数显示名
- 参数类型
- 是否必填
- 默认值
- 示例值
- 校验规则
- 表单组件类型
- 排序号
- 帮助说明

前端根据模板动态渲染表单：

- input
- select
- date
- month
- number
- radio
- checkbox
- textarea
- json-editor（高级模式）

## 6.4 查询执行模块

该模块是业务执行核心。

标准执行流程：

1. 接收前端或外部系统传入参数
2. 校验参数合法性
3. 加载接口配置
4. 加载参数模板
5. 组装明文 data
6. 生成 SM4 密钥
7. SM4 加密业务报文
8. SM2 加密 SM4 密钥
9. 组装 header/body
10. 调用目标接口
11. 接收响应
12. 解密响应
13. 标准化结果
14. 记录调用日志
15. 返回结果

技术实现建议：

- 查询执行服务命名为 `query_executor_service`
- 外部接口适配命名为 `remote_api_adapter`
- 每种特殊接口规则实现策略类
- 默认实现统一适配器 + 特殊实现覆写

---

## 6.5 结果标准化模块

由于后期会有多个接口，不同接口的返回格式可能不同，因此必须做标准化。

建议统一返回结构：

```json
{
  "success": true,
  "code": "0",
  "message": "success",
  "traceId": "xxx",
  "interfaceCode": "xxx",
  "requestTime": "2026-03-16 10:00:00",
  "durationMs": 123,
  "data": {},
  "rawData": {},
  "analysisData": {},
  "exportable": true
}
```

说明：

- `data`：标准化后的核心结果
- `rawData`：原始解密响应
- `analysisData`：供图表和分析使用的结构化结果
- `traceId`：链路追踪标识

---

## 6.6 结果分析模块

后期要支持“结果分析”，建议在第一版就预留。

推荐技术：

- pandas
- numpy
- 规则引擎式分析函数
- ECharts 展示

建议支持：

1. 同比分析
2. 环比分析
3. 趋势分析
4. 分组汇总
5. TopN 排名
6. 维度筛选
7. 指标计算
8. 图表展示所需数据结构输出

设计建议：

- 分析逻辑不要直接写在 Controller
- 单独封装为 `analysis_service`
- 针对不同接口类型，可挂接不同分析器
- 采用“结果解析器 + 分析器”策略模式

---

## 6.7 导出模块

后期明确有导出需求，因此必须设计为独立能力。

推荐导出类型：

- Excel
- CSV
- JSON
- PDF（后续可选）

推荐技术：

- openpyxl
- pandas
- 临时文件存储 + 下载链接返回

导出策略建议：

### 小数据量
- 同步导出，接口直接返回文件流或下载地址

### 大数据量
- 异步导出
- 生成任务记录
- 轮询任务状态
- 导出完成后返回下载地址

导出模块建议能力：

1. 原始结果导出
2. 标准化结果导出
3. 分析结果导出
4. 图表截图导出（后续可扩展）
5. 批量查询结果打包导出

---

## 6.8 日志审计模块

政务类和接口类平台必须重视日志。

建议日志分层：

### 业务日志
- 查询开始
- 查询结束
- 参数校验失败
- 接口响应失败
- 分析完成
- 导出完成

### 调用日志
- 请求 URL
- 请求头摘要
- 请求参数明文（按脱敏规则）
- 请求密文摘要
- 响应密文摘要
- 解密结果摘要
- 耗时
- 状态码
- 错误堆栈

### 审计日志
- 谁新增了接口
- 谁修改了 token
- 谁变更了公钥
- 谁执行了高敏查询
- 谁导出了数据

### 安全要求
- token 不记录明文
- 公钥可记录，私钥不落库（如果未来涉及）
- 敏感字段脱敏存储
- 日志表支持按时间分区或归档

---

## 6.9 开放平台模块

由于后续有“别的业务系统要调用本系统”的需求，建议从一开始就建设内部开放能力。

建议能力：

1. 开放 API 凭证管理
2. 调用方白名单
3. 接口级授权
4. 频率限制
5. 调用日志追踪
6. 标准返回码
7. 错误信息规范化

建议开放模式：

### 模式一：同步查询 API
其他系统传入参数，本系统实时查询并返回结果。

### 模式二：异步任务 API
其他系统发起任务，本系统后台执行，稍后通过任务查询接口获取结果。

### 模式三：标准结果订阅 / 推送
后续可扩展，不作为一期重点。

## 8. 关键非功能性要求

## 8.1 安全要求

- token 存储加密或最少脱敏展示
- 所有核心配置仅后端可见
- 前端不直接调用第三方真实接口
- 所有查询必须走本系统后端代理
- 支持操作日志留痕
- 支持敏感字段脱敏
- 支持接口访问权限控制
- 支持调用频率限制
- 支持 IP 白名单（开放 API 场景）

## 8.2 性能要求

- 常规查询响应时间控制在 1~3 秒内（取决于外部接口）
- 接口配置与参数模板优先走缓存
- 大数据分析与导出采用异步任务化
- 高频查询结果可短时缓存
- 支持后续横向扩展

## 8.3 稳定性要求

- 外部接口异常要可重试
- 接口请求必须设置超时
- 异常返回必须标准化
- 关键流程必须有 traceId
- 查询日志不可缺失
- 支持接口级熔断和降级预留

## 8.4 可维护性要求

- 严格分层
- 配置优先于硬编码
- 加密适配器独立封装
- 多接口采用策略模式扩展
- 分析能力独立封装
- 导出能力独立封装
- 对外开放 API 与内部管理 API 分离

## 11. 对 Cursor 的开发约束建议

以下内容建议作为 Cursor 开发约束同步使用：

### 11.1 通用约束
- 必须使用前后端分离架构
- 后端使用 FastAPI
- 前端使用 Vue3 + TypeScript + Element Plus
- 数据库按 MySQL 8 兼容 SQL 编写
- 所有接口配置与模板配置可扩展，不允许写死单接口规则
- 所有第三方接口调用统一走适配层
- 所有 SM2/SM4 加解密统一封装，不允许散落在业务代码中

### 11.2 后端约束
- 严格按 controller / service / adapter / model / schema 分层
- Controller 不写复杂业务逻辑
- 查询执行必须通过 `query_executor_service`
- 外部接口调用必须通过 `remote_api_adapter`
- 加密逻辑只能放 `adapters/crypto/`
- 所有关键操作必须记录日志
- 所有返回必须统一响应结构
- 所有异常必须统一处理

### 11.3 前端约束
- 查询页面必须支持动态表单渲染
- 结果展示至少支持 JSON 视图和表格视图
- 导出功能必须独立封装
- 图表展示与表格展示解耦
- 不得在前端保存 token、公钥等敏感配置
- 不得在前端实现第三方接口真实加密调用

### 11.4 扩展性约束
- 新增接口时应尽量通过配置完成
- 若出现特殊接口，再增加策略类，不得直接修改主流程
- 新增分析能力应通过分析器扩展
- 新增导出格式应通过导出器扩展
- 对外开放 API 必须与后台管理 API 分层隔离
